# 领域知识驱动的科研助手：目标与实现规划

> 本文保留完整目标。实施范围已收缩为单论文项目、约 200 篇资料：文献/文件级回溯足够，页码式号可选。第一版已实现来源归档、方法/公式卡与实验草案，详见 SMALL_PROJECT_GUIDE.md；其余能力仍是规划。

## 1. 用户真正需要的帮助

面对数据和文献，科研新手往往不知道该提出什么问题、选择什么实验、使用什么公式、如何解释结果，以及失败后该做什么。

本项目的目标是让 Agent 能够：
- 按研究目标建立和维护领域知识库；
- 利用知识库提出有依据的竞争解释与研究思路；
- 为用户的数据选择并设计可执行实验；
- 在授权与工具能力范围内组织计算或生成实验操作方案；
- 追踪运行产物，判断实验究竟回答了什么；
- 设计有针对性的补充分析，并把新知识和项目经验送回知识库。

“领域专家”是一种需要通过评测验证的能力目标，不是增加一些文档后自动获得的身份。知识库提供可追溯依据；Agent 完成推理，研究者可以检查、纠正和选择路线。

## 2. 从数据请求到研究方案的默认流程

```text
用户：上传数据，问“应该做什么研究、收集哪些知识、设计哪些实验？”
    ↓
界定目标与输入：研究对象、想回答的问题、数据结构、限制
    ↓
检查是否已有相关领域知识库
    ├─ 已有：核查覆盖范围、来源和新鲜度，补足本任务缺口
    └─ 没有：先建立本任务所需的最小知识库
    ↓
领域知识与数据匹配：定义、测量、假设、方法条件、局限
    ↓
给出多个有依据的实验候选及优先次序
    ↓
形成可审查的实验计划和执行说明
    ↓
在用户已授权范围内执行计算，或交付供人执行的实验方案
    ↓
读取真实产物，分开观察、解释与判断
    ↓
针对未决问题设计补充分析
    ↓
追加项目经验，必要时提出领域知识修订
```

### “先建知识库”的具体含义

Agent 应先检查并建立知识库，而不是要求新手先自行完成一套知识工程。已有相关库可复用；库不足时由 Agent 提出检索范围并组织材料。

初始阶段可以检查文件类型、字段、单位、时间范围、样本组织和缺失标记，用于确定应该收集什么知识。这不等于在没有依据时先确定模型或给出实质性科研结论。

“最小”不是固定篇数：推荐的方法须有已核查来源、适用条件和当前数据的匹配说明。无法获得关键来源时，应给出缺口和候选研究路线，不能把候选路线包装成已获支持的执行方案。

### 为新手交付的第一份结果

1. **目标理解：** 哪个问题来自用户，哪个是 Agent 建议的研究问题。
2. **知识库清单：** 已纳入哪些文件、读到哪些部分、还缺哪些专业知识。
3. **数据诊断：** 当前数据能支持什么，关键缺口是什么。
4. **候选实验表：** 每条路线要解决的问题、依据、数据需求、成本、风险、结果分支。
5. **建议先做的一步：** 为什么优先，它会影响哪个后续选择。

## 3. 三类知识共同工作

| 层 | 保存内容 | 作用 | 更新条件 |
| --- | --- | --- | --- |
| 领域知识 | 定义、理论、公式、方法、实验协议、适用条件、已知局限和争议 | 提供设计与解释依据 | 新来源核验、来源修订、发现冲突 |
| 项目知识 | 研究目标、数据版本、假设、实验计划、运行、产物、解释与决策 | 让领域方法适配当前研究 | 真实项目进展与核验过的产物 |
| 研究经验 | 在什么条件下什么方法有用、何时失败、例外、重开条件 | 避免重复弯路，帮助后续选择 | 由项目证据支持并明确范围 |

单个项目结果不自动升级为领域共识。论文作者的主张、Agent 的解释、用户的经验也不能合并成一个无来源的“事实”。

多个知识库须保留各自标识、主题、版本与适用范围。引用应至少能定位到 kb_id、对象 ID 和版本；跨库整合时要检查术语、单位、总体和实验条件是否一致。目前代码只有 real/demo 隔离，没有完整的多知识库管理能力。

## 4. 知识来源与文件归档

| 输入 | 目标处理方式 |
| --- | --- |
| 用户上传论文或预印本 | 保存本地文件、文件哈希、书目信息、版本、页码与章节锚点 |
| 用户上传图书或章节 | 保存用户提供文件；保留书名、版本、章/节、印刷页码与文件页码 |
| 用户指定网址 | 记录原网址、获取时间和可用的本地 HTML/PDF/文本快照；保留段落或小节锚点 |
| Agent 主动搜索 | 保存检索问题和筛选理由；取得并核对可用正文后入库，不把搜索摘要当成已阅读全文 |
| 用户给出的专业经验 | 保存原始说明为文件，标注用户经验及适用条件；不能伪装成文献结论 |
| 本项目运行结果 | 保存运行清单、代码和配置版本、输入版本、日志、表图及分析说明 |

归档文件保存在本地资料库，默认不随公共代码仓库上传。只能保存有权访问和使用的材料；无法获取全文时保留元数据和访问限制，不能声称具备全文回溯。网页不可完整归档时，应标记实际保存范围及证据限制。

提取文本、OCR、公式解析和分块都是原文件的派生物，要记录所用工具/版本与相互映射。不能只保留一份改写摘要，丢失其原始出处。

## 5. 每条实验、每个公式都能回到文件

### 回溯链

```text
实验步骤 / 公式 / 分析选择
    → 依据条目或推导记录（ID + 版本）
    → 可选位置（页/节/式/表/图/段落）
    → 本地来源文件（路径 + SHA-256 + 来源版本）
```

网页也需要可查的本地快照；DOI 或 URL 本身不足以满足“文件回溯”。引用文件存在和哈希正确只是结构检查，还需要确认来源确实支持当前用途，不强制填写页码。

### 三种依据类型

| 类型 | 必须说明 | 不允许的做法 |
| --- | --- | --- |
| 直接采用 | 原始文件，具体位置可选，引用的方法与当前条件是否匹配 | 只给一篇主题相关的论文就称其支持全部步骤 |
| 有依据的改造 | 基础方法来源、改动内容、改动理由、新增假设和验证方式 | 将 Agent 修改后的方案标成原作者的方法 |
| Agent 原创新设计 | 支撑设计的知识条目、推理过程、实验目的、局限与待验证条件，保存为本地设计文件 | 为原创步骤编造一条“文献同款”出处 |

原创设计不必在某篇论文中逐字出现；但必须回溯到明确的知识基础与本次设计记录。若连必要基础都未核实，应标为待查的构想，不能进入“证据已就绪”的执行计划。

同一实验可以混合这三种类型，必须按关键步骤标注。所有影响结论的公式、检验、归一化、阈值和数据变换都应进入相应的依据映射；纯工程操作可归入运行清单。

### 公式卡的最小内容

- 名称、版本、用途及数学表达式；
- 符号含义、单位、数据输入和输出；
- 前提、定义域、参数条件、不能使用的情形；
- 直接来源文件及式号/页码等锚点；
- 若为变形或推导：原式引用、逐步推导、新增假设、检查结果和推导文件；
- 若有实现：代码位置/版本、数值检查和数据映射。

公式解析须核对下标、上下标、符号和条件。表达式看起来正确，不等于适用于当前数据。

### 实验卡的最小内容

- 要回答的问题与竞争解释；
- 为什么当前数据和预算适合做它；
- 对照、变量、样本组织、执行步骤和所用公式；
- 每项关键方法选择的来源或设计依据；
- 预期结果分支及各自允许与不允许的结论；
- 参数确定方式、停止条件和补充分析触发条件；
- 计划版本；执行后关联运行与产物，不能用计划冒充结果。

## 6. Agent 如何“指挥实验”和“判断实验”

### 执行前

将方案转为操作步骤，说明输入、依赖、命令/协议、预期输出、检查点和预算。知识库不自动赋予工具权限；只在用户已授权范围内运行，涉及新数据外传、额外费用或实质性范围改变时遵守相应授权边界。

### 执行中

计算实验可以由具备工具的 Agent 调度，记录退出状态和产物。实体实验通常由研究者操作，Agent 提供方案、检查表与记录模板，不能声称自己完成了未执行的实验。

失败运行、缺失文件、质量异常应记录实际状态，不能补造结果。

### 执行后

1. 核对计划与实际执行是否一致，记录偏离及原因。
2. 检查产物完整性和数据质量。
3. 提取 Observation，再讨论 Interpretation。
4. 对照知识库的适用条件，判断哪些解释得到支持、削弱或仍未区分。
5. 更新建议与未决问题，提出必要的补充分析。

补充分析必须对应明确的问题：检查稳健性、某个假设、数据质量或竞争解释。标注事先计划还是结果出来后新增，保留所有相关结果，不能反复挑选分析只保留有利输出。

## 7. 例子：新手上传一份实验数据

假想用户：“这是多个样品的测量数据，我不知道该查哪些知识、做什么实验。”

**第一步，界定问题。** Agent 检查字段与单位，明确样品、测量条件和研究目的。若“提高预测准确率”与“解释作用机制”尚未选定，应说明两者需要不同证据。

**第二步，建立任务知识库。** 归档用户指定论文、图书章节及网址；针对测量原理、对照设计和候选分析方法补充检索。交付知识条目及来源文件清单，不直接拿某个熟悉的模型套数据。

**第三步，匹配条件。** 将当前数据的重复结构、缺失项和测量条件与方法假设对应。缺少关键元数据时，先提出补录或核查动作。

**第四步，给出路线。** 例如：先排查测量条件变化、比较可比条件下的样品差异、评估替代解释。这里仅为路线类别；选定具体检验、模型和公式前必须具备对应来源与适用性核对。

**第五步，执行和判断。** 在授权范围内运行选定分析，归档产物；把信号差异与机制解释分开，设计能处理剩余疑点的补充分析。

**第六步，更新。** 项目结果形成有条件的经验，后续 Agent 读取它时还要检查是否适用，而不是把一次结果当成通用规则。

本例是目标流程示意，不是本仓库已完成的实测案例。

## 8. 知识库怎样补充与修订

1. **收集：** 用户输入或 Agent 检索，登记来源及访问状态。
2. **核验：** 检查文件、版本、可定位性、提取质量与阅读深度。
3. **组织：** 提取定义、方法、公式和局限，区分作者表述与 Agent 推断。
4. **关联：** 将知识连接到待解决的问题、数据条件和候选实验。
5. **更新：** 新来源或运行产物形成提案；在允许的接口和授权范围内追加版本。
6. **复核：** 找出可能受影响的公式、实验和决策，标记待审查；不要自动认定全部失效。
7. **保留：** 保存旧版本、矛盾证据和修订理由，后续会话可恢复过程。

不应把互相矛盾的来源“平均成”一个结论。争议本身也是知识条目，需要标明各自适用范围与未解决问题。

## 9. 从当前原型到目标产品

| 模块 | 当前状态 | 下一步交付 |
| --- | --- | --- |
| 研究状态、对象版本、精确引用、demo/real 隔离 | 已有基础 | 保留并扩展到知识与运行对象 |
| 论文/图书/网页本地归档 | 第一版已支持本地文件和哈希版本 | 自动抓取、解析与阅读仍需后续工具 |
| 方法/公式卡 | 第一版已有草案字段与来源引用 | 科学适用性由 Agent 与研究者核对 |
| 多知识库检索与选择 | 尚未实现 | kb_id、跨库引用和领域/任务范围 |
| 数据条件与方法适配 | 尚未实现可验收工作流 | 数据概要、假设匹配、缺口诊断 |
| 有依据的实验计划 | 第一版可保存逐步带依据的草案 | 执行与真实结果登记尚未开放 |
| 实验调度和运行登记 | 尚未实现 | 计算运行清单、输入输出关联、失败状态 |
| 结果判断与补充分析 | Skill 有部分原则 | 从产物到解释的审查流程及记录 |
| 真实知识/实验更新 | 目前仅定制摘要登记 | 受控真实写入、来源核验与影响复核 |

建议实施顺序：**来源归档与回溯 → 方法/公式卡 → 数据适配与实验卡 → 运行登记和结果判断 → 真实更新与多库管理。** 先完成一个小问题的端到端案例，再扩大知识规模。不能靠增加 README 或 Skill 文字替代缺失的软件能力。

## 10. 验收标准

- 新项目无相关库时，先建立可核查的最小任务知识库，再推荐具体执行方案。
- 论文、图书和网页三类输入均可回到已登记的本地文件（具体位置可选）。
- 每个推荐实验的关键方法和每个使用公式均有依据映射；无法核验的项目清楚标为缺口。
- Agent 改造与原创新设计有单独记录，不冒用原文出处。
- 数据条件不满足时，Agent 能调整、暂停或提出补数据，而不是强行运行方法。
- 计算结果能回到实际运行、代码、输入和输出；没有产物就没有已完成的实验结论。
- 新证据出现后，能解释哪些建议改变了、哪些没改变，以及为什么。
- 新会话读取记录后能够恢复理由链；不混淆摘要、原文、设计和实际运行。
- 自动结构检查与领域专家对科学适用性的审查分别报告；软件通过不代表科研能力通过。
